# 分阶段交付运行手册

本手册规定阶段如何规划、执行、验证和交接。这里记录稳定流程；项目特定步骤应写入 `plans/`。

## 1. 阶段契约

每份阶段计划必须定义：

- 目标：一个可观察结果。
- 范围：本阶段交付的行为。
- 非目标：明确排除的诱人事项。
- 依赖：开始前必须具备的事实或制品。
- 入口门：开始前必须满足的条件。
- 任务：有顺序、范围明确的实现单元。
- 验证：命令和人工检查。
- 证据：能够证明结果的文件或输出。
- 退出门：声明完成所需的客观条件。
- 回滚或降级：阶段失败时仍可保留的安全状态。
- 交接：下一阶段、遗留风险和下一步。

## 2. 入口门

开始实现前：

1. 与用户确认阶段目标和验收标准。
2. 阅读权威规格和上一阶段证据。
3. 检查工作树并保留无关修改。
4. 解决依赖和执行门。
5. 找出最高风险假设，并安排尽早验证。
6. 确认预计修改的文件，以及明确不修改的区域。

如果某项依赖仍不明确，应将阶段标记为 `blocked`，不能静默猜测契约。

## 3. 执行循环

对每项任务：

1. 重述本次要改变的可观察行为。
2. 在可行时先增加或识别一个失败的验证切口。
3. 完成最小且完整的修改。
4. 立即运行聚焦验证。
5. 检查差异中是否混入无关修改和敏感信息。
6. 记录证据，或准确说明无法执行检查的原因。
7. 仅在阶段计划仍然有效时继续。

遇到以下情况应停止并重新规划：

- 所需范围明显扩大。
- 上游契约与规格冲突。
- 当前架构无法满足验收标准。
- 破坏性或外部可见操作需要新的授权。
- 工作树与用户无关修改发生冲突。

## 4. 验证阶梯

先使用能够证明当前单元的最小检查，阶段收尾前再逐步扩大：

1. Schema 或纯单元检查。
2. 聚焦模块测试。
3. 类型检查和代码检查。
4. 集成测试。
5. 生产构建。
6. 主流程和失败流程人工检查。
7. 必要时进行浏览器或部署环境验证。

未执行的检查绝不能记为通过。必须区分 `passed`、`failed`、`blocked`、`not_run` 和 `existing_failure`。

## 5. 退出门

只有满足以下条件，阶段才能标记为 `verified`：

- 每条验收标准都有证据。
- 主流程和至少一个有意义的失败流程经过检查。
- 必需的自动化检查通过，或限制已被明确接受。
- 最终差异仅包含已确认范围。
- 不存在调试代码、凭据、临时文件或过期生成物。
- `STATE.md` 已反映当前事实。
- 下一阶段的入口条件已经明确。
- 用户确认阶段边界后才继续推进。

使用以下交接格式：

```text
阶段：<名称>
结果：verified | blocked | deferred
交付：<可观察结果>
证据：<链接或命令>
遗留风险：<具体列表>
下一道门：<下一步必须满足的条件>
下一动作：<一个具体动作>
```

## 6. Git 与外部操作

- 每个完整任务或阶段检查点优先形成一个可回滚提交。
- 不得包含无关工作树修改。
- 不得通过跳过钩子换取绿色提交。
- 未得到用户对相应操作的授权，不得推送、部署、发布、提交比赛或修改外部系统。
- 公开发布前，必须从干净环境验证仓库、开源协议、在线地址和使用说明。

## 7. 范围纪律

- 优先交付完整而狭窄的纵向切片，不交付多个半成品功能。
- 基础设施工作必须解锁可观察的阶段结果。
- 只有当前退出门通过后，才能开始增强项。
- 刻意简化必须写入非目标，并注明升级条件。
